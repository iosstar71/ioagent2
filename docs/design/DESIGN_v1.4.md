## A. VOC · 결함 개편

### A-1. 원칙
- VOC 는 **접수 대장**: 모든 단계 · 모든 판정이 한 목록에 남는다. 모수 = 전체 접수(삭제 제외).
- 칸 두 개로 나눈다 — **발생 단계**(언제 접수됐나, 자동) · **판정**(분석 결과, PL 이 정함).
- 작은 개선은 VOC 안에서 처리. 큰 개선만 PL 이 [추가 요구사항으로 등록] (산출물 부담 방지).
- 테스트 결함 현황 = **통합테스트 단계 + 판정 결함** 만. 안정화는 VOC 현황에만.
- 새 입력 부담 최소: 단계는 자동, 심각도는 판정이 결함일 때만 보임.

### A-2. 자료 (`vocData`) 변경

| 필드 | 지금 | 1.4 | 비고 |
|---|---|---|---|
| `vocType` | VOC · 버그 · 이슈 | **판정**: 미판정 · 결함 · 개선 요청 · 설명 종결 · 이슈 | 필드 이름 유지(엑셀 · 병합 호환), 값 목록만 바뀜 |
| `stage` | 없음 | 요건분석/설계 · 구현/단위테스트 · 통합테스트 · 안정화 | 새 필드. 접수일로 자동, 사람이 고치면 `stageManual: true` |
| `severity` | 없음 | 치명 · 높음 · 보통 · 낮음 | 새 필드. 판정 = 결함일 때만 입력 · 표시 |
| `reqLink` | 없음 | 등록된 추가 요구사항 ID | 새 필드. [등록] 때 자동 |
| `closedDate` | 없음 | 완료 · 요구 반영이 된 날 | 새 필드. 상태가 끝남으로 바뀔 때 자동(기준일), 다시 열면 지움. 결함 소진 차트용 |
| `status` | 대기 · 진행 · 완료 · 제외 · 보류 · 삭제 | 대기 · 진행 · 완료 · 보류 · **요구 반영** · 삭제 | "요구 반영" 은 [등록]으로만 됨. "제외" 정리는 결정할 것 ① |

- 우선순위(`priority`)는 그대로 (처리 순서). 심각도와 따로 둔다 — 심각도는 결함의 영향, 우선순위는 처리 순서.
- 정의는 `Metrics` 에 한 곳: `VOC_JUDGE`, `VOC_STAGES`, `VOC_SEVERITY` (화면 · 엑셀 · 상세 패널이 읽어 씀, 복사 금지).

### A-3. 단계 자동 지정
- 서브시스템의 SDLC(또는 개선과제) 유형 Phase 마다 **4단계 중 하나로 매핑** (`phase.vocStage`).
  - 처음에는 Phase 이름 · 키워드로 추정: 분석 · 설계 · 요구 · 착수 · Fit-Gap → 요건분석/설계 / 개발 · 구현 · 단위 · 설정 · 이터레이션 → 구현/단위테스트 / 테스트 · 검증 · 인수 · 리뷰 · QA → 통합테스트 / 이행 · 안정화 · 오픈 · 릴리즈 · 종료 → 안정화
  - 프로젝트 설정 > Phase 일정 표에 "VOC 단계" 열 하나 추가 — 추정이 틀리면 여기서 고침.
- VOC 의 단계 = 접수일이 들어가는 Phase 계획 기간(`pStart~pEnd`)의 매핑 단계.
  - 기간이 겹치면 늦게 시작한 Phase, 어디에도 없으면 앞뒤로 가장 가까운 Phase. Phase 일정이 없으면 빈 값(사람이 고름).
  - 접수일 · 서브시스템 · Phase 일정이 바뀌면 다시 계산. 단 `stageManual` 이면 그대로.
- 계산 함수: `Metrics.vocStageOf(reqDate, phases)` (DOM 없음 → 단위 시험).

### A-4. 판정 · 상태 흐름
```
접수(미판정, 대기) ─ 분석 ─┬ 결함      → 진행 → 완료
                          ├ 개선 요청 → (작은 것) 진행 → 완료
                          │            (큰 것)   [추가 요구사항으로 등록] → 요구 반영
                          ├ 설명 종결 → 완료 (조치 칸에 설명 · "#VOC-012 와 중복" 등)
                          └ 이슈      → 진행 → 완료
```
- 미판정은 상태와 무관하게 "판정 대기" 로 따로 셈.

### A-5. 추가 요구사항 등록
- 버튼 위치: VOC 상세 패널(RecordPanel) — 판정이 "개선 요청" 이고 아직 등록 전일 때만 보임.
- 확인 대화상자(`openConfirmDialog`): "추가 요구사항으로 등록합니다. 이후 일정 · 산출물은 요구사항에서 관리합니다."
- 만들어지는 요구사항(`reqMasterData`):
  - `id`: **추가 요구사항 접두사**로 서브시스템별 번호 (결정할 것 ③, 예 `CR-MES-001`). 프로젝트 설정 > ID 접두사에 한 줄 추가
  - `system` · `name`(= VOC 제목) · `priority` 복사, `status` 대기
  - 새 필드: `origin`: "추가"(없으면 초기), `srcVoc`: VOC ID, `addedDate`: 기준일
- VOC 쪽: `status` = 요구 반영, `reqLink` = 새 REQ ID, `closedDate` = 기준일.
- 되돌리기: 요구사항을 삭제하면 VOC 의 `reqLink` 를 비우고 상태를 대기로 (확인 대화상자에서 안내).
- 요구사항 목록: ID 옆 "추가" 칩 + 출처 VOC 링크, 걸러 보기 "초기 / 추가".

### A-6. 집계 기준 (`Metrics` — 모든 화면 · 보고서가 이것만 씀)

| 함수 | 셈 |
|---|---|
| `vocStats(list)` | 지금 결과 + `byJudge`{판정별} + `byStage`{단계별 × 판정별} + `undecided` + `toReq` |
| 처리율 | (완료 + 요구 반영) ÷ (삭제 제외 전체) |
| `vocOpen(list)` | 삭제 · 완료 · 요구 반영 이 아닌 것 (보류는 미결이지만 지연 판정 제외 — 지금 규칙 유지) |
| `defectStats(list, refDate)` | 단계 = 통합테스트 · 판정 = 결함: 전체 · 미결 · 심각도별 · 일별 누적(발생 · 해결 · 잔여) |
| `reqStats(list)` | 지금 결과 + `initial` · `added` (`origin`) |
| 범위 증가 | 개선 요청 건수 ÷ 접수, 그중 요구 등록 · VOC 처리 |

- 요구 반영 VOC: 모수 · 판정별 건수 포함, 처리된 것으로 셈, 미결 · 지연 · 체크할 일 제외, 결함 현황 제외. 요구사항 현황에서는 "추가" 로 셈.

### A-7. 화면
**메뉴 이름**: "VOC" → **"VOC · 결함"** (결정할 것 ⑤). 화면 ID(`tab-voc`)는 그대로.

**VOC · 결함 목록** (`req-voc.js`)
- 열: ID · **단계** · **판정** · 서브시스템 · 우선순위 · (심각도 — 판정 결함일 때만 값, 아니면 "-") · 제목 · 요청자 · 접수일 · 목표일 · 상태 · 조치
- 걸러 보기: 도메인 · 서브시스템 · **단계** · **판정** (지금 "구분" 대체) + 상태 칩
- 위 통계 줄: 접수 · 판정 대기 · 결함 · 개선 요청(등록 n) · 설명 종결 · 이슈 · 처리율
- 열 정의는 배열 한 곳에서 머리글 · 행을 함께 만든다 (CLAUDE.md 1-2 정리 항목 — 이 화면을 고치므로 함께)
- 판정 대기 행은 옅은 경고 표시(`--warning` 틴트)

**상세 패널** (`record-panel.js` `SCHEMAS.voc`): 단계 · 판정 · 심각도(결함일 때) · 연결 요구사항 · [추가 요구사항으로 등록]

**VOC 현황 표** — 대시보드 · Phase 현황에 "단계 × 판정" 표 (A 안의 예시 표). 합계 행 `.col-total`.

**테스트 결함 현황** — 통합테스트 단계 접수가 1건 이상일 때만
- 대시보드: 카드(전체 · 미결 · 치명/높음 미결 · 해결률) + **결함 소진 차트**(일별 누적 발생 · 해결 선, 잔여 막대; `dashboard-chart.js`, 색은 `--chart-*`)
- Summary(Home): 한 줄 "결함 n건 · 미결 m (치명 k) · 판정 대기 j"
- Phase 현황: 통합테스트 매핑 Phase 행에 결함 · 미결 열
- 체크할 일(`CheckList`): "판정 대기 VOC" 묶음 추가 (PL 이상)

**요구사항 현황** — 초기 n / 추가 m (항상 표시). Phase 현황 · 대시보드 요구사항 표에 열 하나.

**범위 변경 알림 (선택)** — 서브시스템의 VOC 처리 개선 요청이 설정 건수(기본 10, 0 = 끔) 이상이면 Summary 에 "범위 협의 검토" 알림.

### A-8. 보고서
- 주간보고(`weekly-report.js` 스냅샷 · 서식): VOC 줄을 "신규 n (결함 a · 개선 b · 판정 대기 c) · 미결 m" 으로. 결함 현황이 있으면 "결함 미결 m (치명 k)" 한 줄.
- 종합보고서(`exec-deck.js`): `SECTIONS` 에 `defect`("테스트 결함 현황" — 카드 + 소진 차트 + 심각도 표) 추가. 결함 자료가 없으면 건너뜀. 종합형 · 상세형 프리셋에 포함. `reqvoc` 장표의 요구사항 열에 초기/추가.
- 엑셀 다운로드 · 업로드(`excel-sync.js` 열 정의): VOC 시트 열 = 단계 · 판정 · 심각도 · 연결 요구사항 · 종료일 추가, 요구사항 시트 = 구분(초기/추가) · 출처 VOC · 등록일 추가. 예전 열 이름 "구분"은 판정으로 읽음(값 변환 A-9). 시트 이름은 그대로.

## B. 기준선 비교

### B-1. 원칙
- 입력 거의 없음: [기준선 확정] 버튼 한 번으로 그 순간의 계획 일정을 복사해 둠.
- 기준선은 여러 번 확정 가능(재기준선) — 매번 **사유 필수**, 이력으로 남음. 비교는 "최초" 또는 "직전" 중 선택(기본 최초).

### B-2. 자료
- `projectConfig.baselines`: `[{ no, date, by, reason }]`
- `wbsData` 새 필드: `bStart` · `bEnd` (현재 비교 기준선의 계획 일정), 이력용 `bHist: { [no]: [bStart, bEnd] }` (Leaf 만; 상위는 계산)
- 확정 뒤 새로 생긴 Task 는 기준선 없음 → "기준선 후 추가" 표시

### B-3. 계산 (`wbs-engine.js`, 단위 시험)
- Task 차이 = 계획 종료 − 기준선 종료(영업일, 기존 `progressBasis` 따름). +면 밀림.
- 서브시스템 · 프로젝트 = 마지막 Task 종료일 차이.
- "기준선 대비 지연 Task" = 차이 > 0 인 Leaf 수.

### B-4. 화면
- **프로젝트 설정 > 기준선**: [기준선 확정] (PM 이상), 이력 표(번호 · 날짜 · 사람 · 사유), 비교 기준 선택.
- **Gantt**: 계획 막대 아래 얇은 회색 막대(기준선). 보기 옵션으로 켜고 끔.
- **WBS 상세 패널**: "기준선 2026-03-02 ~ 04-10 (+5일)".
- **WBS 표**: 접은 열 묶음에 "기준선 차이" 열(펼칠 때만).
- **Summary · 대시보드**: "종료 예정 기준선 대비 +N일 · 밀린 Task n건" + 최근 재기준선 사유.

### B-5. 보고서 · 엑셀
- 주간보고 · 종합보고서 `summary` 장표에 기준선 차이 한 줄, `delay` 장표 표에 "기준선 차이" 열.
- 엑셀 WBS 시트: 기준선 시작 · 종료 열(다운로드만, 업로드 때는 읽지 않음 — 기준선은 버튼으로만 바뀜).
